# Архитектурные решения

## ADR-001 — Модульный монолит

**Статус:** принято. Django-приложения отражают предметные границы, но разворачиваются единым backend. Причина: короткий срок MVP, общие транзакции и отсутствие подтверждённой потребности в микросервисах.

## ADR-002 — React SPA и версионированный REST API

**Статус:** принято. Интерфейс на React/TypeScript, API имеет префикс `/api/v1`. Контракт можно развивать независимо от серверного HTML и позже использовать в мобильном клиенте.

## ADR-003 — JWT access/refresh

**Статус:** принято. Короткоживущий access-токен и refresh-токен. Клиент хранит сессию в `sessionStorage`; для production рекомендуется перейти на защищённый httpOnly cookie через BFF/edge.

## ADR-004 — Отдельные User и Employee

**Статус:** принято. Сотрудник может существовать до выдачи доступа или после его отзыва, а учётная запись не содержит кадровые поля.

## ADR-005 — Роли с областью доступа

**Статус:** принято. `UserRole` хранит роль и необязательные company/facility scope. Проверки выполняются сервером. Суперпользователь имеет глобальный доступ.

## ADR-006 — Демо-данные только через seed-команду

**Статус:** принято. Все вымышленные данные создаёт идемпотентная команда `seed_demo`; они явно отмечены `is_demo` и не смешиваются с production-данными.

## ADR-007 — Управляемый автомат состояний задач

**Статус:** принято. Бизнес-переходы (`accept`, `start`, `submit`, `approve`, `return`) являются отдельными API-действиями, проверяют роль участника и исходный статус. Прямое закрытие исполнителем исключено. Каждый переход записывается в `TaskHistory`.

## ADR-008 — Неизменяемый результат чек-листа

**Статус:** принято. При завершении сохраняется снимок версии шаблона и набор ответов больше не редактируется. Нарушения создаются сервером по типу и границам вопроса и связываются с автоматически созданной задачей.

## ADR-009 — Один активный инцидент на событие датчика

**Статус:** принято. Инцидент связан с `SensorEvent` отношением один-к-одному. Повторные критические показания обновляют пик активного события и не создают дубликаты. Нормализация показателя выполняется сервисом приёма показаний.

## ADR-010 — Объективная формула эффективности

**Статус:** принято. Итог за 30 дней: 40% соблюдение сроков, 25% качество приёмки, 20% чек-листы, 15% реакция на инциденты. Отсутствие событий не штрафует сотрудника; субъективная оценка не смешивается с измеримыми показателями.

## ADR-011 — База знаний как отдельная предметная граница

**Статус:** принято. `knowledge_base` является отдельным Django-приложением модульного монолита. Оно ссылается на существующие `User`, `Employee`, `Role`, `Department`, `Facility`, `Region`, `Task` и журнал аудита, не дублируя их.

## ADR-012 — Неизменяемая версия ознакомления

**Статус:** принято. Назначение обязательного ознакомления фиксирует конкретную `MaterialVersion`. Публикация новой версии не изменяет историю подтверждений; при флаге повторного ознакомления создаются новые назначения.

## ADR-013 — Правила доступа с запретом по умолчанию при наличии правил

**Статус:** принято. Опубликованный материал без правил доступен всем авторизованным сотрудникам компании владельца. Если правила заданы, сотрудник должен совпасть хотя бы с одним правилом по сотруднику, роли, должности, подразделению, объекту или региону. Создание и управление доступны владельцу и руководящим ролям; проверки выполняются на backend.

## ADR-014 — Защищённые файлы материалов

**Статус:** принято. Файлы хранятся в существующем persistent media volume, но их URL не выдаются сериализатором. Скачивание выполняется отдельным API-действием после проверки прав, расширения, MIME-типа и настраиваемого лимита размера.

## ADR-015 — Прогресс обучения рассчитывает доменный сервис

**Статус:** принято. Frontend не может напрямую менять процент и статус назначения. Сервис завершения урока проверяет сотрудника, принадлежность урока курсу и обязательное подтверждение, после чего пересчитывает прогресс по обязательным урокам и завершает курс атомарно.

## ADR-016 — Тестирование отделено от прохождения уроков

**Статус:** принято. Этап моделей курсов не содержит временной упрощённой модели тестов. `Assessment` и попытки добавляются следующей миграцией; тогда завершение курса будет переводиться в `WAITING_ASSESSMENT`, если итоговый тест обязателен. Это сохраняет чистую историю миграций и сервисные границы.

# iikoCard / iiko Cloud — этап 1

## Ограничение суммы карты питания — 10.09.2026

Уточнение пользователя: редактируемая сумма питания не может превышать 10000 ₽.
CreateInput.validate проверяет тип по scoped UUID категории и отклоняет превышение
на prepare/create до обращений к iiko и создания операции. HTML max меняется по
типу; диапазон питания 0.01–10000, по умолчанию 10000. Остальные типы сохраняют
обязательный ввод с прежним техническим пределом. Сумма не обрезается молча.

## Актуально: создание с пополнением — 10.09.2026

Пользователь утвердил AYS Sheregesh для всех типов; сумма питания по умолчанию 10000 ₽ (можно изменить), для остальных ввод обязателен. Сумма topupAmount обязательна в API, положительна, до 2 знаков после запятой, максимум 9999999999.99 (локальная точность хранения). Она нормализуется и включается в HMAC запроса/подтверждение; изменение требует новой подготовки. При переключении типа формы сумма сбрасывается. Старые клиенты без суммы не запускают запись.

Кошелёк сервера фиксирован в области Шерегеша: 03bf0000-6bec-ac1f-5d42-08de178c0e2a. Перед любыми записями проверяется активная программа с этим walletId. После создания, категорий и проверки карты читается исходный баланс. Миграция iiko.0007 сохраняет topup_amount, topup_wallet_id, topup_balance_before и topup_confirmed. Этап topup_wallet и событие Audit/Outbox сохраняются до POST /api/1/loyalty/iiko/customer/wallet/topup. Payload: organizationId, customerId, walletId, sum и технический комментарий с operationId.

API не предоставляет idempotency key; комментарий служит только для поиска операции. Повторов записи нет даже при 401/timeout. Резерв операции предотвращает повторное пополнение, включая новый operationId того же номера после неопределённого результата. После ответа читаются тот же владелец и баланс: прирост должен точно совпасть с суммой. Несовпадение/недоступность чтения остаётся needs_review; обновление статуса ничего не доначисляет. Конкурентное изменение баланса тоже приводит к сверке, не к повтору. Итоговый succeeded ставится только с topup_confirmed=true. Старые успешные записи остаются без пополнения.

Для создания с пополнением требуется новое право card.topup наряду с card.create; чтение старых операций остаётся по прежним правилам. superuser пользователя уже имеет доступ. Проверки синтетические; реального начисления в ходе разработки не выполняли.

## Актуальная механика: удаление прежнего гостя — 10.09.2026

Пользователь уточнил: в iiko вручную удаляет гостя вместе с картой и создаёт нового. Это заменяет описанную ниже прежнюю механику card/remove. Новый вызов POST /api/1/loyalty/iiko/delete_customers отправляет customerIds=[подтверждённый прежний UUID] и organizationId. По контракту это логическое удаление; уничтожение истории и физическое удаление данных не обещаются.

Подтверждение показывает прежний профиль, все карты, категории, комментарий и балансы и прямо разрешает удаление гостя целиком. Старые подписи не принимаются: в подписанные данные добавлен replacementMode=delete_guest_v1. Требуется card.delete_guest вместо прежнего card.reassign (либо superuser). Перед записью профиль снова сверяется со снимком.

Успешный HTTP200 недостаточен: требуются точные целочисленные счётчики total=1/deleted=1/notFound=0, чтение прежнего UUID с isDeleted=true и подтверждённое отсутствие номера и треков выбранной карты. Если удалённый гость по ID недоступен с неопределённой ошибкой или карта не освободилась, цепочка остаётся needs_review; новый гость не создаётся. Балансы/история не переносятся. Автоповторов и восстановления гостя нет. Данные удалённых гостей исключены из предупреждений ФИО. Реальный вызов delete_customers при разработке не выполнялся.

## Предупреждение ФИО и подтверждённая передача — 10.09.2026

Добавлен `POST card/prepare/`: валидированная форма + operationId, только чтение iiko.
Он показывает прежнего владельца занятого номера (ФИО, ID, все карты, категории,
кошельки/балансы) и возможные совпадения имени/фамилии. Телефон, email, track и полный
профиль не отдаются. Ввод изменён — прежнее подтверждение сбрасывается.

KnownGuest — частичный индекс наблюдавшихся гостей внутри connection/organization:
UUID гостя, HMAC нормализованных имени и фамилии, время наблюдения. Нормализация:
Unicode NFKC, регистр, пробелы, ё/е. Отчество не исключает кандидата: предупреждение
показывает живое ФИО, включая наличие/отсутствие отчества. Имена открытым текстом
в индексе не хранятся. Индекс обновляется проверкой карты, preview и успешным созданием.
Локально добавлены три ранее проверенные пользователем карты, включая эталон и 55100.

В API iiko нет полного поиска по ФИО: интерфейс явно сообщает неполное покрытие.
Проверяется до 20 известных кандидатов; недоступность части кандидатов или превышение
лимита также требуют подтверждения предупреждения. Лица из production People не
объединяются автоматически с внешними гостями, однофамильцы не блокируются жёстко.

Preview выдаёт подписанное подтверждение на 15 минут, связанное с пользователем,
operationId, подключением/организацией, HMAC всей формы и снимками регистрации/совпадений.
При совпадении ФИО нужен confirmDuplicates=yes. Для занятого номера отдельно нужны
confirmReplacement=yes и право `iiko.sheregesh.card.reassign` GLOBAL (либо superuser)
в дополнение к праву создания. Флажки из браузера без валидного подтверждения недостаточны.
Форма показывает снятие именно регистрации выбранной карты и нового получателя;
финальная кнопка — «Удалить регистрацию и создать на нового владельца».

Перед записью заново читаются данные. Смена владельца/карты/категорий/балансов или
формы, другой пользователь, истёкшее подтверждение останавливают операцию. Непосредственно
перед удалением выполняется ещё одна сверка снимка. Проверяется однозначность card ID,
номера и фактического track. Если будущий track (номер) принадлежит иной карте,
переназначение блокируется. Track остаётся только на сервере.

`customer/card/remove` вызывается ровно один раз с прежним customerId и фактическим
track. Профиль гостя не удаляется. Затем проверяются сохранение старого гостя и всех
других карт, отсутствие целевой регистрации и освобождение номера/старого и нового
track. Только после этого создаётся новый гость с картой и назначаются категории.
Кошельки, баланс и история старого гостя не переносятся и не изменяются этой операцией.
Между системами нет атомарной транзакции: ошибка/timeout удаления или проверки не
запускает создание; ошибка после удаления оставляет явный needs_review, а не ложный
успех. Автоматического rollback или повторного удаления нет.

Журнал хранит предыдущий customerId; Audit/Outbox отмечают подтверждение, снятие и итог.
У завершённой прежней операции можно снять только флаг активного резерва, сохранив
её успешную квитанцию. Это происходит атомарно с резервом новой подтверждённой операции.
Незавершённые running/needs_review нельзя вытеснить. Повторный operationId возвращает
сохранённую квитанцию без внешних вызовов.

Локально применена iiko.0005: KnownGuest, previous_customer_id, reservation_active и
обновлённая уникальность активного резерва. Прежние данные не удалялись. Новое право
добавлено в каталог; полномочия обычных пользователей не расширялись. Самостоятельное
удаление без последующего оформления не добавлялось: вкладка проверки направляет в
форму передачи новому владельцу.

## Справочники карт — 10.09.2026

В локальную базу добавлен пользовательский список: 12 подразделений, 6 юридических
лиц и 3 типа карт. Сохранены ранее разрешённые IT и «Без согласования»: всего 23 записи.
Все 21 наименование из нового списка точно совпали с активными категориями живого
каталога iiko, включая «Каритшал». Сопоставление выполнено по уникальному точному
названию при подготовке миграции; в работе используются сохранённые UUID, не поиск
по похожему тексту. Категории в iiko не создавались и не изменялись.

`CardCategory` хранит область connection/organization, поле формы, название,
external_id и порядок. Это справочник соответствий интеграции, а не создание
параллельных production LegalEntity/OrgUnit: для их заполнения нужен отдельный
контекст оргструктуры. `iiko.0002_cardcategory` и `iiko.0003_seed_card_categories`
применены только локально; прежние записи и другие миграции не затронуты.

`GET /api/v1/iiko/connections/sheregesh/card/catalog/` требует право просмотра
или создания карт соответствующего подключения (либо superuser). Форма загружает
списки из БД; до загрузки создание заблокировано, при ошибке доступен повтор загрузки.
При создании сервер проверяет принадлежность каждого ID именно своему полю и области,
затем проверяет в iiko активность выбранных четырёх категорий и отсутствие посторонних
категорий по умолчанию. Назначаются и верифицируются выбранные значения, а не постоянный
эталон. Произвольная категория/ID из другой локации или другого поля отвергается.
При проверке карты все известные категории раскладываются по этим же справочникам;

### Повторы и частичный результат

`CardCreation` — журнал операций интеграции, не параллельный справочник сотрудников.
Никакие People/Organization сущности не создаются по свободно введённому ФИО.
В БД сохраняются UUID операции/гостя, инициатор, область, HMAC отпечатки номера
и формы, состояние/шаг и подтверждённые категории. ФИО, номер, track, токены и
полный ответ iiko не сохраняются в журнал, Audit или Outbox. HMAC использует
стабильный Django SECRET_KEY: при его плановой ротации нужно предварительно
разобрать незавершённые операции; их отпечатки нельзя автоматически пересчитать
без исходных номеров.

Одна квитанция по operationId; одинаковый повтор возвращает её без вызовов iiko,
изменённая форма с тем же ID отвергается. Уникальная частичная DB constraint
резервирует номер внутри подключения/организации для running/succeeded/needs_review,
в том числе между процессами. `failed` означает остановку до первой записи и
позволяет новую попытку. Операции записи не повторяются автоматически ни при 401,
ни при сетевой ошибке. Каждый шаг фиксируется до внешнего вызова. После начала
записи любой неподтверждённый результат становится needs_review; авария процесса
может оставить running. Резерв не снимается по таймеру.

AuditService и DomainEventService записывают начало и итог вместе с локальным
изменением состояния. Ошибка Audit/Outbox до начала не позволяет писать в iiko.
Outbox здесь сообщает локальные факты: обработчики не должны повторять внешние
операции. Если финальный локальный commit не произошёл, сохранённое состояние
running продолжает блокировать повторное создание.

Форма блокирует повторную отправку, показывает шаг и квитанцию, восстанавливает
её по UUID из sessionStorage после reload. Кнопка «Обновить статус» читает локальное
состояние и не возобновляет запись. Для needs_review/зависшего running разработчик
должен прочитать гостя по сохранённому ID в том же кабинете, сверить карту и
категории и определить точечное восстановление. Автоматического rollback,
удаления гостя и освобождения резерва нет. Между preflight и привязкой другой
клиент iiko может изменить данные: распределённая атомарность контрактом не дана.

по неизменяемой конфигурации, результаты гостей не кешируются.

## Проверенный официальный контракт

Источники:

- [Developer Portal](https://public-api.iikoweb.ru/portal/documentation) — доступна оболочка страницы;
- [iiko Cloud docs](https://api-ru.iiko.services/docs) — интерфейс документации;
- [действующая OpenAPI JSON](https://api-ru.iiko.services/api-docs/docs) — получена напрямую по HTTPS 10.09.2026.

Веб-инструмент не смог открыть два URL iiko.services, но прямой HTTPS GET с этого
компьютера успешно вернул актуальную спецификацию. Контракт проверен по живому
официальному источнику, а не по старому AI Kit. В `iiko-openapi-excerpt.json`
сохранены выбранные paths, 48 зависимых schemas, перечень всех paths и webhook-схем.
Пути записи в снимке приведены только для исследования будущего переназначения.

| Операция | URL после https://api-ru.iiko.services | Тело запроса / ответ |
|---|---|---|
| Авторизация | `/api/v2/access_token` | обязательные `apiKey`, `appId`, `clientSecret`; ответ `token`, `correlationId` |
| Организации | `/api/1/organizations` | обязательных полей нет; клиент задаёт `returnAdditionalInfo=false`, `includeDisabled=false`; ответ `organizations` с `id`, `name` |
| Категории | `/api/1/loyalty/iiko/customer_category` | обязательный `organizationId`; ответ `guestCategories` |
| Программы | `/api/1/loyalty/iiko/program` | обязательный `organizationId`, клиент задаёт `withoutMarketingCampaigns=true`; ответ **`Programs` с заглавной P** |
| Гость по карте | `/api/1/loyalty/iiko/customer/info` | `type=cardNumber`, `cardNumber`, `organizationId`; гость, `cards`, `categories`, `walletBalances` |

Авторизация v1 помечена deprecated. Токен v2 — JWT сроком на час; точное истечение
в `exp`, refresh-token flow отсутствует. Клиент читает `exp` только для срока кеша
(не использует неподписанные claims для локальной авторизации), ограничивает срок
часом и обновляет за 60 секунд до истечения. Некорректный/истёкший JWT отвергается.
На 401 чтения — одна повторная авторизация и один повтор операции; повторный 401
сбрасывает токен и завершает операцию ошибкой.

В OpenAPI `appId` имеет format uuid, но противоречащий этому пример `15`.
Клиент передаёт выданный APP ID как строку без преобразования. В базовой схеме
поиска гостя required содержит только `type`; клиент дополнительно требует
валидный UUID организации и непустой номер, чтобы всегда задавать область чтения.
Доступные discriminator-значения: `phone`, `cardTrack`, `cardNumber`, `email`, `id`.
На этом этапе реализован только выборочный поиск `cardNumber`.

Категория: `id`, `name`, `isActive`, `isDefaultForNewGuests`. Программа содержит
`id`, `name`, `programType`, `walletId`, `isActive`, `appliedOrganizations` и другие
настройки; диагностика выводит только эти шесть полей. Баланс гостя:
`id` кошелька, `name`, `type`, `balance`. Типы 0 — депозит/корпоративное питание,
1 — бонусы, 2 — продукты, 3 — скидки, 4 — сертификаты. `balance` нельзя автоматически
трактовать как рубли или как лимит физической карты без проверки типа и правил программы.

Выбранные операции документированы как синхронные ответы 200, без commandId/polling.
Корреляция — идентификатор трассировки, а не признак асинхронности. Ответ 202 не
объявляется успехом. Документированные ошибки: 400, 401, 408, 500;
дополнительно клиент безопасно обрабатывает HTTP 403, 404, 429, 502–504.
Операционные группы доступа: `Data: dictionaries`, `Loyalty: dictionaries`,
`Guests: info`. Численные квоты для ключа в выбранных схемах не указаны.

Спецификация не задаёт однозначный код «карта не найдена». Поэтому 400 остаётся
`bad_request`, 404 — `not_found_unconfirmed`, отсутствие гостя в 200 —
`customer_not_returned_unconfirmed`. Текст ошибки сервера не анализируется как
доказательство отсутствия карты и не печатается. Реальный отрицательный сценарий
нужно подтвердить отдельно с контролируемыми тестовыми данными; случайный номер
рабочей карты не выбирается.

## Секреты, транспорт и изоляция

Используется принятый в проекте формат переменных окружения, без новой БД секретов.
Можно передать process environment либо `--env-file`; файл в этом случае целиком
определяет подключение, без смешивания с переменными другого кабинета. Поддерживается
простой формат `KEY=value`, одинарные/двойные внешние кавычки, комментарии отдельной
строкой; интерполяции, выполнения кода и inline-комментариев нет. Неизвестные и
повторные ключи отвергаются. Корневой `.env` не читается и не перезаписывается.

Файл пилота вне Git и OneDrive:
`C:\Users\riddl\AppData\Local\AYS Connect\.env.iiko.sheregesh`.
Шаблон: `docs/iiko.env.example`; `.env.example` дополнен только безопасными значениями.

| Переменная | Значение / назначение |
|---|---|
| `IIKO_CONNECTION_ID` | `sheregesh`; уникальный постоянный slug кабинета/локации |
| `IIKO_APP_ID` | локально выданный APP ID |
| `IIKO_CLIENT_SECRET` | локальный секрет приложения |
| `IIKO_API_KEY` | локальный ключ Шерегеша |

| `IIKO_READ_TIMEOUT` | 20 секунд на сетевую операцию чтения/записи после connect |
| `IIKO_MAX_RETRIES` | 2; диапазон 0–2 |

Для второго кабинета создать отдельный локальный файл с другим CONNECTION_ID и
его реквизитами. Один `IikoClient` держит одно неизменяемое подключение и собственный
токен в памяти; экземпляр следует переиспользовать для повторных чтений. Общего
кеша, Redis-ключа или кеша ответов нет. Каждая отдельная CLI-команда получает свой
токен. Результаты маркируются `(connectionId, organizationId)`; внешний ID никогда
не должен становиться единственным ключом будущего сопоставления. Future mapping:
`(connection_id, organization_id, entity_type, external_id)` с возможным явным
объединением организаций только после подтверждения общей области кабинета.

TLS проверяется стандартным CA-хранилищем Python, отключения проверки нет.
Разрешён только проверенный RU hostname без path/query/userinfo, перенаправления
не выполняются; другие регионы потребуют отдельной проверки и изменения allowlist.
HTTP proxy из окружения не используется. Connect и socket timeout обязательны
(предел 120 секунд каждый), ответ ограничен 4 MiB. Это socket timeout, а не общий
wall-clock deadline всего batch из 11 организаций.

Сетевые сбои, HTTP 408/429/500/502/503/504: не более двух повторов с задержками 1/2
секунды; Retry-After поддерживает секунды и HTTP-date. При Retry-After >10 секунд
команда возвращает ошибку без раннего повторения. TLS/400/403/404 не повторяются.
Тела запросов, токены, cardTrack, ошибки транспорта и errorDescription не логируются.
В диагностике остаются локальный код ошибки, HTTP status и проверенный UUID
correlationId, если он был возвращён. В текущих loyalty-ответах correlationId отсутствует.

Реквизиты необходимо редактировать в самом локальном файле и сохранять, а не
прикладывать как комментарии к diff. В этой сессии пользователь передал реквизиты
в комментариях; значения перенесены только в локальную конфигурацию. Пользователю
рекомендована замена Client Secret и API-ключа, поскольку комментарии входят в историю
задачи. Значения в документацию, Git и вывод диагностических команд не включались.

## Точные команды локальной диагностики

PowerShell из корня проекта. Подготовлен `.venv` на Python 3.12 с backend/requirements.txt.

```powershell
$aysPython = '.\.venv\Scripts\python.exe'
$iikoEnv = "$env:LOCALAPPDATA\AYS Connect\.env.iiko.sheregesh"
$iikoOrg = '07727ae8-4b93-4529-ac85-9232fae45be3' # Восточка / RMS 6

& $aysPython .\backend\manage.py iiko_probe programs --organization $iikoOrg --env-file $iikoEnv
& $aysPython .\backend\manage.py iiko_probe catalogs --env-file $iikoEnv
```

`config` не делает сетевых запросов и выводит только наличие/валидность параметров.
`catalogs` читает категории и программы всех доступных организаций, независимо
фиксирует ошибки каждой операции, выводит количества и SHA256 отсортированных
проекций для сравнения. Не читает гостей. Ненулевой exit code при любой ошибке.
Индивидуальные команды categories/programs показывают выбранные поля справочника.
JSON экранирует Unicode и управляющие символы для совместимости терминалов Windows.

Тестовая карта — только явно выбранная пользователем. Можно ввести номер скрытым
приглашением в интерактивном терминале:

```powershell
& $aysPython .\backend\manage.py iiko_probe card --organization $iikoOrg --env-file $iikoEnv
```

Либо вписать **только номер карты**, без кавычек, в локальный

Номер не передаётся в argv/history, ведущие нули сохраняются. В результате только

## Категории, поиск, дальнейшее освобождение карты

Категории принадлежат **гостю**: `customer/info.categories`; несколько карт гостя
находятся в `customer/info.cards`. Следовательно, по контракту эти карты приводят
к одному набору категорий и кошельков гостя; независимых категорий для каждой карты
в этом ответе нет. Практическую проверку нескольких карт пока не выполняли.

Совпадающие внешние ID наблюдались у всех точек данного кабинета. Глобальная
уникальность и общность справочников между кабинетами спецификацией не гарантированы.
Область организации сохраняется даже при совпадении ID; разные подключения не смешиваются.

Серверный поиск гостей по одной категории или их AND/OR-сочетанию в действующей
спецификации не найден: перечислены только пять критериев единичного customer/info.
Произвольные недокументированные фильтры не отправлялись; обещания такого поиска нет.
Будущий локальный индекс может содержать только уже известных из заявок гостей
с выборочным обновлением по id, но не будет полным индексом кабинета. Для полного
поиска потребуется отдельно согласованный источник изменений/экспорта и правила ПДн.

Есть `customer/transactions/by_revision`: обязательны customerId, pageSize,
organizationId, курсор revision и lastTransactionId. Это **транзакции известного
гостя**, не лента изменений гостей/категорий. В опубликованных webhook-схемах
обновления профиля или категорий гостя не обнаружены. Синхронизация/новые webhook
настройки не запускались; необходимость другого API следует уточнять у iiko.

Будущая передача пластика: документированы `customer/card/remove` (customerId,
cardTrack, organizationId) и `customer/card/add` (customerId, cardTrack, cardNumber,
organizationId). Они не реализованы и не вызывались. Удаление гостя для этой цели
не требуется предполагать: гость может иметь другие карты и общие кошельки.
Гарантия сохранения истории самой регистрации карты и атомарности remove/add
в этих схемах не дана. Следующий этап должен спроектировать локальную историю
владения, права, Audit/Outbox, восстановление после частичного сбоя и проверить
повторное использование номера/track на тестовом контуре. Удаления и переназначения
в рамках этой работы не выполняются.

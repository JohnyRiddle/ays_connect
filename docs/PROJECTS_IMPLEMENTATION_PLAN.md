## Audit of the actual code

Production People has `Employee`, `Team`/temporal `TeamMembership`, `OrgUnit`, `Location`, `LegalEntity`, `AssignmentTarget` and resolver. Teams are collaboration groups, not a substitute for Project lifecycle or mandatory participant semantics; a Project may reference an existing Team but must support members across org units. Work is `work_tasks.Task` with immutable locked sequence, optimistic version, acceptance policy frozen after first publication (including DB trigger), templates, comments and protected attachments. `SourceType.PROJECT` is available; `backend/tasks` is legacy. Work SPA and `workApi.ts` already target `/api/internal/v1/`. RBAC uses the Permission registry/EmployeeRole and SQL-filtered Work selectors. Audit and transactional Outbox are shared; production Notification Core has idempotent intents, channel preferences and protected delivery. No canonical Task dependency engine is present; blocked dependency metrics are deferred explicitly.

## Domain design

New `projects` app: `Project` (UUID, immutable PRJ sequence, goal/result, manager/customer Employee, OrgUnit/Location, planned/actual dates, DRAFT/ACTIVE/ON_HOLD/COMPLETED/CANCELLED, separate archive, version, author/timestamps); `ProjectMember` with MANAGER/MEMBER/OBSERVER and active uniqueness/history; flat `ProjectStage`; `ProjectMilestone` with required criterion, deadline, responsible and confirmation history; project comments and protected attachments. Never create a second task lifecycle. Link one Work Task to at most one Project and at most one Stage of that Project. Keep old tasks unlinked. Enforce stage/project equality in PostgreSQL across ORM/bulk/Admin paths with an append-only constraint/trigger, plus service checks; migration remains append-only. Project progress is completed/(all except cancelled), REVIEW incomplete, zero denominator “Нет задач”, 100% does not auto-complete. Every aggregate exposed to a partial-scope user is over `TaskSelector.visible_to()` and labelled as such.

## Commands, access and concurrency

Project and link transitions are explicit services using row locks/version, Audit and Outbox in one transaction. Project completion checks all tasks and required milestones without revealing hidden task data. ON_HOLD/CANCELLED do not silently transition tasks. Task reopen in a completed Project atomically activates the Project with reason/history/manager notification; archived or cancelled Project rejects until explicit restoration/unlink. Project create-from-task and template-create wrap existing Work service and link in the same transaction; failure rolls back Task/Audit/Outbox. Link/move/unlink require project permissions on source/target and existing Work visibility/edit rights. A Project participant alone never gains global Work access. New codes `project.view/create/edit/members_manage/structure_manage/task_link_manage/lifecycle/comment/attachment_add/attachment_delete`; registry only, no auto-grants to existing production roles.

All Project-mutating commands take a project-scoped PostgreSQL advisory transaction lock before row locks. Where Work Task is involved the order is Task → Project → Stage/link after the advisory lock; Project-only completion uses the same advisory lock, so it cannot race Project task creation/link/reopen. Existing standalone Work commands remain unchanged. Double links use a unique Task constraint; create commands need an idempotency key. Verify parallel link, create/complete, reopen/complete and stage deletion/assignment on PostgreSQL.
